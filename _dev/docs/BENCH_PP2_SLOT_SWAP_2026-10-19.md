# 双 170HX 换槽后的 PP=2 复测（2026-10-19）

问题：两张 CMP 170HX 换了插槽，一张进了芯片组 PCIe 槽；本项目此前测过两张卡 PP 跑
`Qwen3.8-Flash-Next-AutoRound-3bpw-MTP` 的速度，问这次有没有变化。

结论先说：

1. **链路侧确实变差了，而且量正好是"槽位砍半"**：跨卡 20 MiB 的 PP 预填边界
   **6.64 → 13.06 ms（1.97×）**；单卡 H2D 带宽也正好 2×（x8 1.71 GB/s vs x4 0.85 GB/s）。
2. **模型侧看不出量级变化**：8k 上下文下预填 ~0.64 s、MTP 解码 ~76 tok/s，
   相对 10-16 基线分别是 −4% 与 −4%，都在本机日间波动范围内；无 MTP 臂整体慢 8-10%，
   **超出链路能解释的量**（见 §5），更像主机侧干扰而不是插槽。
3. 复现时注意：**3090 现在也在机器里**（bus 0B，CUDA 0），PP 必须
   `CUDA_VISIBLE_DEVICES=1,2` 才能选中两张 170HX。
4. **插槽换回 CPU 直连后（10-20 00:43）复测**：链路、PP MTP 解码、TP=2 预填全部回到
   10-16 基线（20 MiB 6.70 ms、MTP 解码 80.0 tok/s、TP=2 冷预填 2.150 s）；无 MTP 臂
   仍低 ~7%，说明那 7% 与插槽无关。见 §8。

---

## 1. 拓扑：换槽前后

从 10-15 的 NCCL 冒烟日志可以反推换槽前的状态（`_dev/out/smoke_c_r0.log`）：

- rank0 `nvmlDev 1 busId c000`、rank1 `nvmlDev 0 busId b000` → 两张 170HX 在 **bus 0B / 0C**。
- 这两条总线挂在 CPU 根端口 `00:03.1` / `00:03.2` 下，即**两个 CPU x8 槽**，各 x8。
- 当时机器里只有这两张卡（`hw_snapshot_20261015_2200.txt` 只有 GPU 0/1）。

现在（Windows PnP 父链 + `nvidia-smi`）：

| 卡 | PCI bus | 父链 | 槽位性质 | 当前宽度 |
|---|---|---|---|---|
| 170HX `06011618` | `04:00.0` | `00:01.2 → 02:00.0 → 03:02.0` | **X570 芯片组下游**（同链上还有 2.5G 网卡/Wi-Fi/USB） | **x4** |
| RTX 3090 | `0B:00.0` | `00:03.1` | CPU 根端口 | x8 |
| 170HX `f897f9ac` | `0C:00.0` | `00:03.2` | CPU 根端口 | x8 |

即：**一张 170HX 从 CPU x8 槽挪到了芯片组 x4 槽，3090 占了空出来的 CPU 槽**。
两张 170HX 的 UUID 与 10-15 日志一致（`06011618` / `f897f9ac`），是同一对卡。

CUDA 枚举顺序与 `nvidia-smi` 不同：**CUDA 0 = 3090、1 = 170HX@0C、2 = 170HX@04**。
本轮所有 PP 运行都显式 `CUDA_VISIBLE_DEVICES=1,2`，让 **stage 0（含 PLE 层）留在 CPU x8 卡**、
stage 1 落在芯片组 x4 卡 —— PLE 的 95.37 GiB SSD 流式读走 host→GPU，放在宽的那条链上更合理。

## 2. 链路实测（静默主机）

工具：`_dev/probe/_pcie_link_probe.py`、`_dev/probe/_nccl_comm_smoke.py`。

| 指标 | 10-15（两卡都 CPU x8） | 10-19 现在 | 变化 |
|---|---|---|---|
| NCCL `send/recv` 20 MiB（一个 2048-token 预填边界） | **6.64 ms** | **13.06 ms**（CPU→芯片组）/ 12.60 ms（反向） | **1.97×** |
| NCCL `send/recv` 4 KiB（一次 decode 边界） | 0.10 ms | 0.09 / 0.12 ms | 持平 |
| NCCL `all_reduce` 16 MiB | 8.69 ms | 16.77 / 17.15 ms | 1.93× |
| 单卡 H2D / D2H 512 MiB pinned | —（未测） | x8 卡 1.71 / 1.67 GB/s；**x4 卡 0.85 / 0.84 GB/s** | 2× |
| NVML 空闲读数 | — | 两张 170HX 都是 gen1；x4/x8 | — |

两点判读：

- **20 MiB 的 2× 与宽度 x8→x4 完全对得上**：瓶颈是芯片组那条 x4 链，约 1.6 GB/s 有效；
  10-15 两卡 x8 时约 3.2 GB/s。不是"代数掉了"，也不是别的。
- decode 边界（4 KiB）**没有变**：PP 解码每步只搬 5 KiB，插槽影响不到它。
  这决定了后面模型侧解码不该有明显变化。

### 2.1 一条重要的方法论教训：主机拷文件会把链路测量翻倍

第一轮测量（22:45）正好撞上用户在拷文件，同一套冒烟得到：

| 主机状态 | 20 MiB | all_reduce 16 MiB | MTP 4k 填充解码 |
|---|---|---|---|
| 拷文件中（22:45-23:02） | **25.6 ms** | 33.4 ms | **53.0 tok/s** |
| 磁盘静默（23:09 后） | **13.06 ms** | 16.8 ms | **134.7 tok/s** |

主机 I/O 争用会把跨卡搬运和 MTP 解码同时拖慢一倍以上 —— 用户指出后已全部在静默窗口重跑，
**本文所有结论只用静默窗口的数据**。`_dev/out/logs/` 里 22:59 那组 MTP 日志作废。

本轮 = 换槽后、主机静默、逐项同参数重跑。预填用**唯一 salt** 绕开前缀缓存，
并读 `usage.prompt_tokens` 核对真实长度（约 3,871 tok，不是脚本假设的 4,000）。

## 4. 换算成"每条 PP 边界值多少"

- 一个 2048-token 预填 chunk 的 hidden = 2048×2560×2 B = **10 MiB** →
  边界 3.3 ms（旧）→ **6.5 ms（新）**，即 **+3.2 ms/chunk**。
- 4k 预填 = 2 个 chunk → **+6.4 ms**，在 0.64 s 上约 **+1%**。
- 32k 预填 = 16 个 chunk → +51 ms；262k = 128 个 chunk → +410 ms（都是约 +1%）。
- decode 边界 4 KiB **没有变化**（0.09-0.12 ms），所以解码理论上不该被插槽影响。

**即：链路确实慢了 2×，但 8k/长上下文预填里它只占 ~1%，解码里占 0。**

## 5. 那 8-10% 的无 MTP 差距怎么解释？

不是链路。按 §4，链路最多解释预填 +1%、解码 0。剩下的候选：

1. **3090 现在在机器里并驱动显示器**（1.3-1.4 GiB、WDDM），10-16 时不在。
   它吃主机内存带宽/PCIe 资源，也会让 Windows 合成器常年有活。
2. PP 每一步有两处跨进程同步（hidden send + sampled-token broadcast）；
   如果 broadcast 走的是 gloo/CPU 组（`PP_VS_TP_WINDOWS.md` §4 的已知缺口），
   主机一忙就会加 ~1 ms/步，正好是观测到的 17.4 → 19.3 ms。
3. 本机日间波动：同一台机器、同一份代码，MTP 解码 5 次就能从 72.5 漂到 79.4（±5%）。
   无 MTP 臂没有做多日重复，因此 10% 里有多少是"今天的主机"无法从本轮数据切分。

要把这条彻底钉死，需要一个 **PP=1 同机对照**（单卡 170HX 跑同一模型同一 prompt，
看它相对 9-05 的单卡基线是否也慢了 8-10%）—— 本轮没做，留作下一步。

## 6. 复现命令

```powershell
# 只让两张 170HX 可见（CUDA 0 是 3090）
$env:CUDA_VISIBLE_DEVICES='1,2'
# PLE × PP 的闸门开关（不设会直接 NotImplementedError）
$env:VLLM_PLE_ALLOW_PP='1'

# MTP 臂

# 无 MTP 臂
& _dev\probe\_pp_tp_smoke.ps1 -Mode pp -Size 2 -MaxLen 8192 -LogPrefix pp2_nomtp

# 基准（服务起来后）
python _dev\probe\_pp_bench_slotswap.py --port 9401 --prefill-tokens 4000 --runs 3 --conc 4
python _dev\probe\_longgen.py --port 9401 --max-tokens 256 --label mtp
```

链路：

```powershell
$env:CUDA_VISIBLE_DEVICES='1,2'
python _dev\probe\_pcie_link_probe.py       # H2D/D2H + 当前宽度

```

## 7. 一句话

**换到芯片组槽的那张卡把跨卡链路从 x8 砍到 x4（PP 预填边界 6.64 → 13.06 ms，正好 2×），
但在 8k 上下文、真模型 PP=2 的端到端速度上看不出这个量级的变化：预填 ~0.64 s、MTP 解码
~76 tok/s，与 10-16 基线相差 4% 以内。无 MTP 臂整体慢 8-10%，按边界字节数算不出这么高的
代价，更像 3090 回归/主机侧干扰，需要 PP=1 同机对照才能定论。**

## 8. 补记（2026-10-20 00:43）：插槽换回 CPU 直连

用户把两张 170HX 插回 CPU 直连的两个 x8 槽，3090 移到芯片组槽。同一主机、静默磁盘、
同一套脚本复测。

### 8.1 拓扑与链路

| 卡 | bus | 槽 | 负载下 gen/width |
|---|---|---|---|
| 170HX `f897f9ac` | `0B` | CPU `00:03.1` | **Gen2 x8** |
| 170HX `06011618` | `0C` | CPU `00:03.2` | **Gen2 x8** |
| RTX 3090 | `04` | 芯片组（`03:02.0`） | Gen1 x4（空闲） |

| 指标 | 10-16 基线（CPU x8） | 10-19 芯片组（x4） | 10-20 换回（CPU x8） |
|---|---|---|---|
| NCCL 20 MiB（预填边界） | 6.64 ms | 13.06 ms | **6.70 ms** |
| NCCL 4 KiB（decode 边界） | 0.10 ms | 0.09 / 0.12 ms | **0.07 ms** |
| NCCL all_reduce 16 MiB | 8.69 ms | 16.8 / 17.2 ms | **8.81 ms** |
| 单卡 H2D 512 MiB | — | 0.85 GB/s（x4） | **3.41 GB/s**（x8 Gen2） |

→ 链路完全恢复，反过来也证实 10-19 的 2× 就是 x8→x4。

### 8.2 PP=2 + MTP（8k，graph）

| 指标 | 10-16 基线 | 10-19 芯片组 | 10-20 换回 |
|---|---|---|---|
| 预填 4k | 0.668 s / 5,987 tok/s | 0.640 / 6,048 | **0.615 / 6,356** |
| `_longgen` 解码 | 79.3 tok/s | 76.1 | **80.0**（6 次中位；73.6-83.2） |
| 首 token | 0.192-0.230 s | 0.201-0.233 | 0.189-0.204 |
| KV 池 | 712,157 | 712,157 | **712,157** |

**MTP 臂回到基线**（80.0 vs 79.3，+0.9%），10-19 的 −4% 可以归因于芯片组 x4 那条链。

### 8.3 PP=2 无 MTP

| 指标 | 10-16 基线 | 10-19 芯片组 | 10-20 换回 |
|---|---|---|---|
| 预填 4k | 0.577 s / 6,932 tok/s | 0.622 / 6,223 | **0.600 / 6,487** |
| `_longgen` 解码 | 57.5 tok/s | 51.7 | **53.7**（6 次中位；52.1-53.9） |
| 4 并发每请求 ITL | 36.3 ms | 39.45 | **38.77** |
| KV 池 | 959,010 | 959,010 | **959,010** |

换回后只收回 ~2 tok/s（51.7 → 53.7），**仍比 10-16 基线低 6.6%**。
也就是说这 7% 不是插槽造成的 —— 两张卡都在 CPU x8 时它还在。MTP 臂却回到基线，
说明底层 PP step 没有实质退化（MTP 接受长度略高，抵消了 step 的少量增加）。
剩余候选：3090 现在在机（10-16 时不在）、驱动/主机状态；要定论仍需 PP=1 同机对照。

### 8.4 TP=2（27B dummy，eager，8k）—— 与 10-16 同口径

| 指标 | 10-16（两卡 CPU x8） | 10-20（两卡 CPU x8） |
|---|---|---|
| 预填 4096（**冷**） | 2.149 s / 1,906 tok/s | **2.150 s / 1,905 tok/s** |
| 4 并发解码 | 36.1 tok/s / ITL 93.1 ms | 38.2、35.8 tok/s；ITL 88.9、95.4 ms |
| KV 池 | 989,786 | 992,195 |

TP=2 的冷预填与 10-16 逐毫秒重合（2.150 vs 2.149 s）。
注意第二发 0.635 s 是**前缀缓存命中**（同一 prompt），不是真预填；跨时间比较只能用冷的那发。

### 8.5 更新后的结论

1. **换回 CPU 直连后，链路、PP MTP 解码、TP=2 预填都回到 10-16 基线**；
   10-19 观察到的链路 2× 与 MTP −4% 就是芯片组 x4 槽，现在复现不出来。
2. **无 MTP 臂的 ~7% 差距与插槽无关**（换回后仍在），待 PP=1 同机对照/关 3090 复测归因。
3. 生产复现口径：`CUDA_VISIBLE_DEVICES=1,2`（3090 是 CUDA 0）、`VLLM_PLE_ALLOW_PP=1`、
   `-MaxLen 8192` 起步；预填测量必须每发换 salt，否则第二次就是前缀缓存命中。
